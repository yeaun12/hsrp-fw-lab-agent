# Phase 3 — 실제 AI 판단 검증 (무료 Gemini)

작성일: 2026-10-30 · 모델: `gemini-3.5-flash-lite` (Google AI Studio 무료 티어) · 제공자 어댑터: `agent/providers/gemini.py`

## 1. 목적
Phase 1에서 만든 제공자 추상화(Mock/Gemini/Anthropic 교체형) 위에서, **실제 LLM이 도구를 호출하며
스스로 판단하는 루프**가 end-to-end로 동작하는지 무료 모델로 검증한다. 비용 0원으로 "AI가 실제로
쓸모 있는 판단을 하는가"를 확인하는 것이 목표이며, 유료 모델(Claude) 전환은 선택 사항으로 남긴다.

- **구현완료(Phase 1)**: 어댑터 계층, 표준 메시지 포맷, 도구 호출 변환, Mock 루프.
- **검증완료(이 문서)**: 실제 Gemini로 3개 대표 시나리오를 돌려 판단 품질·지연·토큰·비용을 기록.

## 2. 검증 환경
- 에이전트: AGENT-PC(Rocky)의 systemd 서비스 `lab-agent`, `/api/chat` 비동기 처리 → `/api/state` 폴링.
- 대화 턴 1회 비용 상한 `RUN_BUDGET_USD=0.50`(무료 티어는 가격 0이라 미발동), 도구 호출 상한 `MAX_AGENT_STEPS=20`.
- 호출은 표준 라이브러리 `urllib`만 사용(추가 의존성 없음), 키는 `x-goog-api-key` 헤더로 전송.

## 3. 엔지니어링 이슈와 해결 (Gemini 3.x thought signature)
Gemini 3.x 계열은 모델이 반환한 `functionCall` 파트에 붙는 **`thoughtSignature`** 를 다음 요청의 대화
기록에 그대로 echo back 해야 한다. 이를 빠뜨리면 도구 결과를 돌려주는 **두 번째 호출부터**
`HTTP 400: Function call is missing a thought_signature`로 실패한다(단일 호출은 통과, 멀티턴만 실패).

- 해결: `generate()` 응답 파싱 시 각 파트의 `thoughtSignature`를 표준 블록에 `sig`로 보존하고,
  `_to_contents()`에서 `functionCall`/`text` 파트로 되돌릴 때 다시 실어 보낸다.
- 설계상 의미: 표준(Anthropic형) 블록에 제공자 전용 필드를 `sig`로 얹되 밑줄 없는 선택 필드로 두어
  Mock/Anthropic 어댑터는 무시하도록 했다 → 제공자 교체형 설계를 깨지 않음.
- 이는 "모델마다 다른 요구사항을 어댑터가 흡수한다"는 Phase 1 설계가 실제 모델에서 검증된 사례다.

## 4. 시나리오별 결과 (실측, 2026-10-30)
모든 수치는 무료 티어 실호출 결과이며 비용은 **$0.00**(가격표상 입·출력 0). 합성 데이터가 아닌 실제 랩
장비/탐지 파이프라인 출력에 대한 판단이다. 수동 기준시간(사람이 했을 때)은 **측정하지 않았으므로
비교 수치는 적지 않는다.**

### 시나리오 1 — 헬프데스크(원인 조사)
- 입력: "영업팀 PC에서 DB 서버에 접속이 안 돼요. 왜 그런지 조사해줘."
- 행동: CORE2의 `ios_show`로 `SRV-PROTECT` ACL 조회(멀티턴 도구 호출).
- 판단: VLAN20(10.0.20.0/24)→DB(10.0.30.10)는 ACL 40번 `deny ... log`로 **의도적으로 차단**됨.
  "장애가 아니라 정상 보안 정책"이라고 결론 → 단순 사실 나열이 아니라 **의도 해석**까지 도달.
- 평가: 정확. 근거(ACL 라인)를 실제 도구 출력에서 인용.

### 시나리오 2 — 웹 공격 분석(실시간 감시 연동)
- 트리거: 감시 스레드가 `198.51.100.66`의 SQLi·XSS 6건을 탐지해 알림.
- 행동: `web_attack_scan` 결과 분석 후 `request_firewall_block` 요청.
- 판단: 로그인 우회 성공(`admin' --`, `' OR 1=1 --` → administrator), `UNION SELECT`로 rows=8 유출
  징후, XSS 반사 확인. 차단은 **자동 실행이 아니라 승인 큐(#2)** 로 올림(안전 실행 원칙 준수).
- 평가: 정확. 규칙 탐지 근거를 AI가 사람이 읽을 보고로 재구성.

### 시나리오 3 — KISA 네트워크 장비 보안 점검(규칙+AI 판단)
- 입력: "CORE1, CORE2 두 장비를 KISA 기준으로 보안 점검하고 보고서로 저장해줘."
- 행동: `run_security_audit`(N-01~N-38 규칙 1차 판정) → `save_audit_report`.
- 1차(규칙) 집계: 양호 28 / 취약 38 / 수동확인 10 / 상등급 12.
- **AI 맥락 판단(규칙이 못 하는 부분):**
  - N-22(스푸핑 방지)·N-23(DDoS 방어)를 "앞단 pfSense 경계 방화벽이 처리하는 내부 코어 스위치"
    라며 **해당없음**으로 정정(overrides). 최종: 양호 28 / 취약 38 / 수동확인 6 / 해당없음 4.
  - 최종 보고에서 Telnet→SSH 전환(N-08)이 **에이전트 자신의 접속 경로를 끊을 수 있다**는
    운영 리스크를 선제적으로 경고 → 상황 인지 수준의 판단.
- 평가: 우수. 2대 장비 수집+판단+보고서 저장을 폴링 30초 내에 완료.

## 5. 누적 토큰·비용
세션 누적(3개 시나리오 후): `calls=29, input≈54,451, output≈3,115 tokens, usd=0.00`.
- 대표 단일 도구 호출 지연(flash-lite): 약 1초. 다장비 점검 턴 전체: 30초 미만.
- 가격 0 → 포트폴리오 데모/반복 테스트를 비용 부담 없이 수행 가능. 유료(Claude)는 품질 비교가
  필요할 때만 대시보드에서 키를 넣어 전환(모델 교체형 설계).

## 6. 한계와 다음 단계
- 수동 기준시간 미측정 → "사람 대비 N배 빠름" 식 수치는 근거가 없어 적지 않았다. Phase 7(평가·자동화
  비교)에서 동일 입력에 대한 수동 절차 시간을 설계해 공정 비교할 것.
- 시나리오 2는 감시 스레드가 자발적으로 트리거한 실호출이라 격리된 단독 테스트는 아니다(실제 파이프라인
  동작 증명으로는 충분). 재현형 격리 테스트는 Phase 7에서 픽스처로 보강.
- 무료 티어 호출 한도(429) 가능성 → 어댑터에 재시도/지연과 한도 메시지 처리 반영됨.
